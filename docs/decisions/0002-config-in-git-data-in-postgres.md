# ADR 0002. Конфигурация в Git, оперативные данные в PostgreSQL

- **Статус:** Принято
- **Дата:** 2026-11-27
- **Задача:** NET-475

## Контекст

В Oktell и конфигурация, и оперативные данные (маршруты, графики,
операторы) правятся мышкой в интерфейсе, без истории и ревью.
Часть данных меняется редко и требует ревью (логика диалплана, SBC),
часть — ежедневно и силами супервизоров (состав очередей, операторы,
праздники и переносы рабочих дней, чёрный список).
Если всё положить в Git, каждое добавление оператора станет MR и
выкаткой; если всё положить в БД, логика станет непроверяемой.

## Решение

**В Git** (раскатывается Ansible, проходит ревью и CI):

- конфигурация Asterisk, Kamailio, rtpengine (шаблоны Jinja2 в ролях);
- универсальный входящий движок диалплана и особая логика тенанта
  отдельным файлом (`tenant-<код>.conf`);
- звуки (`sounds/`, через Git LFS);
- схема БД: миграции таблиц Asterisk (Alembic из `contrib/ast-db-manage`
  Asterisk 22) и собственные SQL-миграции; справочные данные (`db/seed/`:
  праздники РК, причины пауз);
- описание тенантов (`tenants/<код>.yml`): код, принадлежность DID тенанту
  (нужна SBC для маршрутизации), хосты, база, языки, папка записей;
- инвентари стендов; секреты будущего прода — только в Ansible Vault.

**В PostgreSQL** (общий кластер, отдельная база на тенанта):

- маршрут каждого DID — какой график, меню, очередь, приветствие;
- графики работы с переносами дней, праздники РК;
- операторы (PJSIP realtime), очереди и их состав (queue realtime);
- чёрный список, причины пауз;
- CDR и queue_log.

Правило разграничения: *принадлежность* DID тенанту — в Git (её видит SBC),
*поведение* DID — в БД тенанта. Новая линия = строки в БД, а не новый код.

## Рассмотренные альтернативы

- **Всё в Git.** Супервизоры не смогут работать без выкатки; ежедневные
  MR на изменение состава очередей.
- **Всё в БД (включая диалплан, например через `ast_config` realtime).**
  Нет ревью, нет тестов в CI, сложно воспроизвести стенд.
- **Отдельная схема на тенанта в одной базе.** Проще эксплуатировать,
  но слабее изоляция прав и сложнее отдельно восстановить один тенант.

## Последствия

- Нужен плейбук проверки дрейфа (`playbooks/check-drift.yml`): ручные
  правки конфигов на серверах должны обнаруживаться.
- Схема БД меняется только миграциями; CI прогоняет их на пустой базе.
- Оперативные данные в БД нужно бэкапить и восстанавливать отдельно
  от Git; для них нужен будет интерфейс (админка — вне текущего объёма).
- Asterisk зависит от доступности PostgreSQL: при недоступности БД
  realtime-объекты не загружаются. Поведение при отказе БД описывается
  в runbook `asterisk-down` и проверяется на стенде.
